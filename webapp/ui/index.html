FD Intake — start a pipeline run

Drop a Functional Design here, then run the pipeline in Claude Code. The pipeline proposes a clean-core solution (key user / developer / side-by-side — or a mix, driven by the requirement) and stops at three checkpoints for your decision.

✋ Checkpoint 1 · Solution

After the release gate: capability-by-capability mode split, objects + verdicts, and the Custom-Object Naming Contract. You approve/adjust/reject the approach and lock the object names before any code is built.

✋ Checkpoint 2 · Code

After the build + code review (Gate 2): the built code file by file with review findings. Comment on any file to request changes, or approve as-is — build happens first, the TD is documented afterward.

✋ Checkpoint 3 · Acceptance

After peer review + challenger: the full package (and, for side-by-side, the BTP prerequisite checklist before deploy). You accept or send specific items back for rework.

Reference

Skills, workflows, MCP servers and agents available in this Catalyst.

🧠 Experience database — team delivery lessons for Public Cloud. Grows with every pipeline run (the package step records new lessons via record_experience). Searchable semantically via find_similar_delivery (Layer 3 — Digital Brain). References: SAP Business Accelerator Hub (APIs/CDS) · SAP Discovery Center (BTP services + pricing).
Writes net-new pipeline lessons back to experience_db.json so teammates get them on next git pull.
✦ Digital Brain — three knowledge layers built into the pipeline. The vector index rebuilds automatically on startup and after every completed pipeline run — no manual step needed. To force an immediate rebuild or pick up a new catalog sync: python mcp-server/vector/build_index.py & python mcp-server/graph/build_graph.py — or call rebuild_vector_index / sync_object_graph from the Playground.

Layer 1 · Live Object Graph

10,736 nodes · 137,843 cross-type edges · 33 business areas. Links released APIs, CDS views and BAdIs by shared business-concept name fragments — handles SAP's three naming conventions (CamelCase CDS, fused API, 3-char BAdI abbreviations). Rebuilt automatically on every catalog sync.

Tools:

get_object_graph — given one object, return all related objects
get_area_map — full released-object landscape for a business area
sync_object_graph — rebuild graph (+ live $metadata enrichment)

Graph: mcp-server/graph/graph.json

Layer 2 · SAP Knowledge Vectors

10,767 documents (74 APIs + 8,928 CDS views + 1,734 BAdIs + experience entries + past runs) indexed with a dual-mode backend: dense semantic embeddings (sentence-transformers, all-MiniLM-L6-v2) when installed, or BM25 TF-IDF fallback (pure stdlib, always available). Finds released objects by meaning, not just token match. Index rebuilds automatically on startup and after completed runs.

Tools:

semantic_search — natural-language search, optional type filter
rebuild_vector_index — rebuild after catalog or run changes

Index: mcp-server/vector/index.json (metadata) · index.npy (dense float32 matrix, dense mode only)

Layer 3 · Experience Graph

Indexes every completed pipeline run (output/*/run.json) and finds the most similar past delivery to a new requirement — surfacing proven extensibility approaches, known BAdIs, and past pitfalls before the agent starts designing.

Tools:

find_similar_delivery — match new requirement to past runs
rebuild_vector_index — picks up new runs automatically

Grows with every completed pipeline run.

Recommended intake sequence

  1. find_similar_delivery — check past runs for proven patterns
  2. semantic_search — find candidate released objects by meaning
  3. get_object_graph — expand to the full related-object landscape
  4. get_area_map — see every object in the business area
  5. check_object_release_state — verify each candidate

Rebuild commands

Vector index rebuilds automatically on startup and after completed runs. Graph also auto-rebuilds on startup (15s delay) and after run completion (60s delay). Use the button below to force an immediate rebuild of both — useful after a catalog sync or installing sentence-transformers:

CLI alternative (same result):

pip install sentence-transformers   # optional: enable dense embeddings
python mcp-server/vector/build_index.py
python mcp-server/graph/build_graph.py

Or call rebuild_vector_index / sync_object_graph from the MCP server directly.

Setup & dependency notes

Layer 1 (graph) & Layer 3 (experience): pure Python 3.9+ stdlib — zero installs. Layer 2 (vectors): TF-IDF fallback is also zero-install. For true semantic search, install the dense backend:

pip install sentence-transformers

The model (all-MiniLM-L6-v2, ~80 MB) is downloaded once and cached locally. No API keys, no network access in offline mode. Layer 1: adjacency-list BFS with name-prefix edge matching · Live mode: sync_object_graph(live_enrich=true) enriches API nodes with OData entity/field names.

Settings

Authentication: no LLM API keys — Claude Code (your session) is the runtime. SAP connectivity (optional, live mode) uses a communication user via environment variables — nothing is stored in files.

Mode & guardrails

Mode above governs the SAP tenant connection (the MCP server stays fully offline unless live mode is set). Separately, side-by-side (BTP) builds fetch public developer docs (CAP, UI5, Node.js, w3schools, npm registry) to ground CAP/UI5 code; SAP Community is cite-only. Key-user & ABAP-Cloud builds make no web calls. Set S4PC_ALLOW_WEB=1 to allow doc fetching on every build.

SAP tenant credentials (env)

To enable live mode set S4PC_MODE=live, SAP_BASE_URL, SAP_COMM_USER, SAP_COMM_PASSWORD and restart. Live mode is read-only, allowlisted & audited.

OData service allowlist

Extend in mcp-server/config.json — a deliberate human-in-the-loop step.

Test connection

Verifies tenant reachability + communication user via the gateway catalog service. In offline mode this demonstrates the guardrail block.

🚀 BTP deploy connections (side-by-side)

Cloud Foundry targets for the optional BTP deploy step. Non-secret fields are saved to disk; all credentials are kept in memory for this session only (never written to a file). Needs the cf CLI + multiapps plugin and mbt installed on this machine.

🧭 New machine / teammate? Connection setup help

Each person connects their OWN BTP account on their OWN machine — sessions are isolated per OS user, so teammates never collide.

1. Install tools (once per machine) — then open a new terminal:

Windows:  winget install --id CloudFoundry.CLI.v8
          cf install-plugin multiapps -f
          npm install -g mbt
macOS:    brew install cloudfoundry/tap/cf-cli@8
          cf install-plugin multiapps -f
          npm install -g mbt

2. For SSO / trial accounts — log in once in a terminal, then leave password/token blank in the panel (session reuse):

cf login --sso -a <YOUR-API-ENDPOINT>    # open the passcode URL, paste code, pick org/space
cf target                                # verify logged in

3. Click "+ Add system", fill in API endpoint + credentials, click Load orgs, pick org + space, save.

🔒 Never paste a real secret into an AI chat — type it into this panel only. Full guide: docs/btp-onboarding.md.

Add BTP system

🔑 CF SSO Passcode (recommended for deployments)

A one-time passcode creates a full OAuth session (access + refresh token) so cf deploy survives the 15-20 min build. Get a fresh one immediately before deploying. Bearer token alone will fail if staging takes >1 h.

🔒 Password and token are session-only — never written to disk, git, or logs. Wiped on restart.
