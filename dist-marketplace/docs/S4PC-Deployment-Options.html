Three findings that drive the recommendation

1 The IP is plaintext prompts. Whoever controls the runtime can read the methodology. This single fact eliminates client-side deployment as an IP-safe option.
2 Work Zone hosts UIs, not compute. A tile can point at a service you host — the client gets the launchpad experience without receiving the accelerator.
3 No LLM key is needed unless the engine moves into a container. Keeping the engine on your own host preserves the existing "no API keys" position entirely.

02 · THE CONSTRAINT

What is actually being protected

The product is the encoded delivery methodology, not the Python around it.

The asset

  • Phase prompts — gates, checkpoints, clean-core rules
  • Skills and agent definitions
  • Governance server + released-object catalogs
  • Accumulated delivery experience

Rebuilding the surrounding application takes a week. Rebuilding this takes years of engagements.

Why packaging does not protect it

  • Prompts are passed on the command line — visible in any process listing
  • Prompts are written to the engine log in plaintext
  • Claude Code must read skills and the MCP server as files on disk
  • A bundled executable is a self-extracting archive — trivially unpacked
Consequence: an .exe distribution gives packaging convenience but no meaningful IP protection. The only reliable control is keeping the runtime on infrastructure you own.

The contractual counterpart

Deliverables (FD, TD, code, tests) transfer to the client. The accelerator that produced them — tool, prompts, catalogs, experience database — does not, with no derivative-works or reverse-engineering rights. Without this clause, a standard work-made-for-hire term can transfer the whole asset.

Applies to every option that follows.

06 · ARCHITECTURE

Option C — BTP-native with a self-hosted runner

Full BTP web tier without placing an LLM credential on BTP.

SAP BTP (your subaccount) YOUR NETWORK ┌─────────────────────────────────────┐ ┌──────────────────────────┐ │ Work Zone ─► HTML5 UI ─► App Router │ │ Runner daemon │ │ │ │ │ ├─ Claude Code (seat) │ │ ▼ │ │ └─ polls for jobs │ │ Backend API (Cloud │ │ │ │ Foundry / Kyma) │◄─────┤ outbound HTTPS only │ │ │ │ jobs │ (no inbound firewall) │ │ ▼ │ └──────────────────────────┘ │ XSUAA · HANA Cloud · Object Store │ │ └─ runs · deliverables · brain │ └─────────────────────────────────────┘ Multi-user, scalable web tier · zero LLM credentials on BTP

Why this shape

  • Same pattern as self-hosted CI runners — familiar to security teams
  • Runner needs outbound HTTPS only, no inbound rule
  • Keeps seat-based LLM billing

Trade-offs

  • Still requires an always-on host you operate
  • Adds a job queue and runner protocol to build
  • Claude Code login needs periodic renewal
Recommended if multi-tenant scale is needed but the no-API-key position must hold.
07 · ARCHITECTURE

Option D — full BTP deployment

Everything in BTP. Requires accepting an LLM credential in the container.

SAP BTP ┌──────────────────────────────────────────────────────────────────┐ │ Work Zone ─► HTML5 App Repo ─► App Router ─► XSUAA │ │ │ │ │ ▼ │ │ Backend + engine (Cloud Foundry / Kyma) │ │ │ │ │ │ │ └──► Claude API ────────┼──► Anthropic │ ▼ (key / IAM) │ or Bedrock │ HANA Cloud Object Store Application Logging │ or Vertex │ catalog + deliverables observability │ │ brain │ └──────────────────────────────────────────────────────────────────┘

Gains

  • No machine of your own to operate
  • Elastic, genuinely multi-tenant
  • Standard SAP operations model

Costs

  • Requires overturning the "no API keys" rule
  • LLM billing moves from seats to consumption
  • Engine rewrite onto the Agent SDK
  • Highest infrastructure spend of all options
If deployed into the client's subaccount instead of yours, this becomes Option E — the client holds prompts, brain and catalogs. Treat that as an IP sale, priced accordingly.
Prompt caching must be preserved in any rewrite — it is why cost is ~$2.25/run today.

11 · PUBLIC CLOUD BRAIN

Why the brain is the commercial asset

The traceability spine is what no competitor can copy from a demo.

business process (L1–L5) └─ scope item └─ requirement ──[fit-to-standard verdict]──┐ ├─ standard configuration │ └─ gap → WRICEF object ────────────────┘ ├─ released objects consumed ◄── built today ├─ generated code + technical design ├─ test cases → defects ├─ roles / authorisations ├─ transport / activation └─ release-note impact ◄── Run-phase payoff

Questions only the spine can answer

  • Which requirements are still gaps?
  • What test coverage does this scope item have?
  • Which roles does this extension require?
  • SAP deprecates X next release — what breaks?

Commercial significance

Upgrade impact analysis is answerable only because every run records the objects it consumed. That is a recurring, contract-renewing capability — and it compounds with each engagement rather than depreciating.

Client engagements stay partitioned; only anonymised lessons enter the shared brain.

15 · SUMMARY

One page to remember

Do

  • Sell outcomes first — Option A, zero cost, zero risk
  • Host it yourself when clients want access — Option B
  • Surface it as a tile in the client's Work Zone
  • Separate deliverables from the accelerator contractually
  • Design the brain contract now, while agents are still at ideation

Do not

  • Ship the runtime into a client subaccount unpriced
  • Rely on an executable for IP protection
  • Add knowledge domains before fixing provenance and stores
  • Connect all 40 agents before proving one vertical slice
  • Assume prompt caching survives an engine rewrite
