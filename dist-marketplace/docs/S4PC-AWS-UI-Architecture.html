Slide 2 — Public Cloud Brain + RAG

Public Cloud Brain — four layers including RAG

Every pipeline phase queries the brain. The RAG layer grounds deliverables in your masked SAP S/4HANA Cloud document corpus — no hallucination, no assumption.

Layer 1 — Object Graph

What: Graph of 8,900+ released SAP objects (CDS views, APIs, BAdIs) and their relationships.

Used for: get_object_graph — tells the engine which BAdI fires at which extension point, which CDS view exposes which fields.

Storage: graph.json on EBS (POC) → S3 + in-memory cache (production)

Layer 2 — Released Object Vectors

What: Dense embeddings of the entire released object catalog — APIs, CDS views, BAdIs described semantically.

Used for: semantic_search — finds the right API or BAdI by meaning, not keyword. "Get open POs for a supplier" → surfaces the correct OData service.

Storage: index.json on EBS (POC) → RDS pgvector (production)

Layer 3 — Experience DB

What: Every completed pipeline run recorded (anonymised — client names hashed before storage).

Used for: find_similar_delivery — surfaces proven approaches for similar requirements. "You solved a vendor invoice extension before — here is what worked."

Storage: experience_db.json on EBS (POC) → RDS pgvector (production)

Layer 4 — SharePoint Document RAG New

What: Harvested SAP S/4HANA Cloud documents from your SharePoint — best practices, process guides, configuration guides, client delivery notes — pulled directly via Microsoft Graph API, masked on EC2, chunked, and embedded.

Used for: At each pipeline phase the engine retrieves the top-K most relevant chunks and injects them as grounded context into the phase prompt. This replaces assumption with evidence from your own delivery knowledge base.

Storage (POC): Embeddings stored in index.json on EBS alongside other brain layers. No S3, no RDS needed. Documents never leave EC2 after processing — SharePoint remains the source of truth.

RAG retrieval flow — per pipeline phase

  1. Pipeline engine begins a phase (e.g. solution design, TD generation)
  2. Engine calls MCP semantic_search with the requirement text as the query
  3. MCP queries local vector index (EBS) — similarity search across all document chunk embeddings
  4. Top-K most relevant chunks (5–10 sections) returned with their text
  5. Chunks injected into the phase prompt as grounded reference context
  6. Engine calls Amazon Bedrock (Claude Sonnet) with context-enriched prompt
  7. Output is grounded in your actual SharePoint documents — not model memory

Document ingest pipeline (scheduled — e.g. nightly)

  1. EC2 authenticates to Microsoft Graph API using Azure AD app credentials (env vars)
  2. Script lists and downloads new/updated documents from SharePoint library
  3. Text extracted from each file (python-docx / PyMuPDF / python-pptx)
  4. Masking applied on EC2 — client names and engagement refs stripped during chunking
  5. Chunks (~500 tokens, 10% overlap) embedded via Bedrock Titan Embeddings
  6. Embeddings written to index.json on EBS alongside released-object vectors
  7. Run POST /api/brain/rebuild to merge new embeddings into the live index
  8. New documents available for RAG retrieval on next pipeline run
POC: No S3, no RDS needed for RAG. All document embeddings live in index.json on EBS — the same file already used for released-object semantic search. The existing brain rebuild mechanism handles the merge automatically. Upgrade to RDS pgvector only when the corpus grows beyond ~50K chunks or when scaling to multiple concurrent clients.
Chunk size: 400–600 tokens with 10% overlap. Masking runs on EC2 during ingest — raw documents never stored outside SharePoint. Azure AD app credentials stored as environment variables only.

UI hosting

#ServiceWhy Needed
8 S3 Bucket — UI Assets Hosts the static UI (index.html). Not publicly accessible — served only via CloudFront using Origin Access Control (OAC).
9 CloudFront Distribution CDN entry point with two origins: / → S3 (UI), /api/* → ALB (API). Single domain eliminates CORS. Caches UI at edge. HTTPS termination.
10 Origin Access Control (OAC) Allows CloudFront to securely read from the UI S3 bucket. The S3 bucket URL is never exposed publicly.

Networking, DNS and security

#ServiceWhy Needed
8 Application Load Balancer (ALB) Sits between CloudFront and EC2. Routes /api/* traffic from CloudFront to the EC2 app. EC2 is never directly accessible — all traffic arrives via ALB.
9 ACM Certificate (us-east-1) Free SSL certificate for your domain attached to CloudFront. Must be created in us-east-1 — AWS requirement for CloudFront regardless of EC2 region. Auto-renews.
10 Route 53 DNS — maps s4pc.yourcompany.com to the CloudFront distribution endpoint so users have a stable, branded address.
11 Security Groups EC2 accepts traffic only from the ALB security group — never from the internet or CloudFront directly. SSH restricted to team IP.
12 VPC (default) Network container for EC2 and ALB. Default VPC is sufficient — no changes needed for this architecture.
13 EC2 Key Pair SSH access for initial setup, app deployments, and maintenance.
14 CloudWatch Logs Captures API server and engine logs for remote debugging and audit trail. Auto-enabled — no setup needed.
One gotcha: ACM certificate region. CloudFront requires its SSL certificate to be in us-east-1 (N. Virginia). Even if your EC2 is in ap-southeast-1 or eu-west-1, the ACM cert for CloudFront must be requested in us-east-1. Create a second cert in your EC2 region separately for the ALB.
Production brain upgrade (RDS pgvector + second S3 bucket) is identical to the previous architecture — add when scaling beyond one client.
Slide 3 — How It Works

Request flow — UI load and pipeline run

Two separate flows share one CloudFront domain. The browser never knows there are two origins.

Flow 1 — Loading the UI

  1. User opens https://s4pc.yourcompany.com in any browser
  2. Route 53 resolves to CloudFront distribution
  3. CloudFront matches path / → routes to Origin 1 (S3 bucket)
  4. CloudFront checks its edge cache — if hit, serves index.html instantly from the nearest edge node
  5. If cache miss, CloudFront fetches from S3 using OAC (signed request), caches it, returns to browser
  6. Browser renders the UI — all subsequent calls go to /api/* on the same domain

Flow 2 — Running a pipeline phase

  1. Browser sends POST /api/pipeline/start to s4pc.yourcompany.com
  2. CloudFront matches path /api/* → routes to Origin 2 (ALB) — no CORS because same domain
  3. ALB forwards to EC2 port 8321
  4. Python webapp spawns claude -p as a detached subprocess (Phase A)
  5. Engine calls MCP server: check_object_release_state, abap_cloud_lint, extensibility_advisor
  6. Engine calls Amazon Bedrock → Claude Sonnet → generates analysis / code / TD
  7. Deliverables written to EBS (output/<RUN-ID>/)
  8. Pipeline pauses at CP1/CP2/CP3 — browser polls GET /api/runs/<id>, UI shows checkpoint
  9. User approves in the UI → engine resumes next phase
  10. Final package available for download via GET /api/runs/<id>/download

CloudFront behaviour rules

  • Cache UI aggressively — set Cache-Control: max-age=86400 on index.html in S3. Invalidate on deploy.
  • Do not cache API responses — CloudFront behaviour for /api/* must have cache disabled (CachingDisabled policy).
  • Forward headers to ALB — Host, Authorization, all cookies must be forwarded so the API works correctly.
  • HTTPS only — redirect HTTP to HTTPS at CloudFront level. EC2 can accept HTTP internally from ALB.

UI deployment — how to update

  1. Edit webapp/ui/index.html locally
  2. Upload: aws s3 cp ui/index.html s3://your-bucket/index.html
  3. Invalidate edge cache: aws cloudfront create-invalidation --distribution-id <id> --paths "/*"
  4. Users see the new UI on next browser refresh — no EC2 restart needed
CloudFront → ALB traffic can use HTTP internally — TLS is terminated at CloudFront. Restrict ALB to accept traffic from CloudFront prefix list only for extra security.

Key reminders

  • No Work Zone needed. Users access via https://s4pc.yourcompany.com — share the URL.
  • No CORS. CloudFront serves UI and API under the same domain — one origin in the browser.
  • UI updates in 30 seconds. Upload new index.html to S3 + CloudFront invalidation — no EC2 restart.
  • ACM cert must be in us-east-1. Hard AWS requirement for CloudFront — EC2 can be in any region.
  • One S3 bucket only. UI assets only — no doc corpus bucket needed for POC.
  • SharePoint stays the source of truth. Documents are never stored outside EC2 EBS after processing — no copy lands in AWS storage.
Total POC services: EC2, EBS, IAM, Bedrock (Sonnet + Titan), S3 × 1 (UI only), CloudFront, OAC, ALB, ACM, Route 53, Security Groups, VPC, Key Pair, CloudWatch + Azure AD app (external). No RDS, no second S3.
