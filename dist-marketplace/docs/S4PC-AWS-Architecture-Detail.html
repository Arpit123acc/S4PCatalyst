Slide 2 — EC2 Internals

What runs inside the EC2

One machine. Four layers. All processes are managed by systemd so they restart on crash or reboot.

Process stack

nginx (port 443 → 8321)

Reverse proxy. Terminates HTTP from ALB and forwards to the Python app. Serves as the process boundary — the Python app never needs to deal with TLS or connection pooling.

webapp/app.py (port 8321)

  • UI server — serves ui/index.html at /
  • REST API — all /api/* endpoints (runs, checkpoints, brain, catalog)
  • Pipeline orchestrator — manages phase sequence, CP gates, run.json state
  • Engine launcher — spawns claude -p as a detached subprocess per phase
  • Atomic write layer — prevents run.json corruption on concurrent requests

Claude Code engine (claude -p)

  • Spawned once per pipeline phase (A → B → C → D)
  • Runs the agentic loop: reads FD, calls MCP tools, generates ABAP/CAP code, writes deliverables
  • Calls Amazon Bedrock for LLM inference via the IAM instance profile
  • Exits cleanly after each phase; resumable from the last completed step

mcp-server/server.py

  • Governance layer — 14 tools wired into every pipeline phase
  • Key tools: check_object_release_state, abap_cloud_lint, extensibility_advisor, find_similar_delivery
  • Pure Python stdlib — zero external dependencies, starts in <1 second
  • Offline-first; never calls an LLM

Slide 3 — End-to-End Flow

How a pipeline run works — step by step

From the user opening a tile to downloading the final deliverable package. ~23 minutes of engine time, 3 human decision points.

Connection & authentication

  1. User clicks the S4PC tile in SAP Build Work Zone
  2. XSUAA / IAS authenticates the user (client's own SSO)
  3. Work Zone destination sends HTTPS request to the ALB URL
  4. ACM terminates SSL at the ALB; ALB forwards to EC2:443
  5. nginx proxies to webapp:8321; UI (index.html) loads in browser

Phase A — Solution design (steps 1–4 + CP1)

  1. User uploads Functional Design (FD) document via the UI
  2. User clicks "Start Pipeline" — webapp creates run.json, spawns claude -p Phase A
  3. Engine reads FD, calls MCP tools: find_similar_delivery, search_released_apis, extensibility_advisor, get_object_graph
  4. Engine calls Amazon Bedrock → Claude Sonnet → generates fit-to-standard analysis + solution options
  5. CP1 — pipeline pauses. User reviews solution options, selects approach, approves naming contract

Phase B — Build (steps 6–7 + CP2)

  1. Engine generates ABAP/CAP code using approved naming contract
  2. MCP: abap_cloud_lint runs on every snippet; check_object_release_state verifies every SAP object
  3. Code review written to 07-code-review.md with findings inventory
  4. CP2 — pipeline pauses. Developer reviews findings, resolves Critical/Major issues, approves code

Phase C — Quality & TD (steps 8–11 + CP3)

  1. Test pack generated (ABAP Unit, API tests, negative tests)
  2. Technical Design document written — 21 sections, Table of Contents, Glossary, Sign-off block
  3. Challenger agent runs adversarial review: upgrade-safety, auth, clean-core, security
  4. CP3 — pipeline pauses. Delivery lead reviews challenger findings, confirms acceptance

Phase D — Package (step 12 + optional 13/14 for BTP)

  1. All deliverables zipped into 12-package.zip
  2. Experience recorded to brain (anonymised, for future similar deliveries)
  3. Deliverables written to S3 bucket (output/<RUN-ID>/)
  4. User downloads package from UI → shares FD, TD, code with client for sign-off

BTP path (14-step variant)

  1. Step 13: BTP Prerequisite Check (human gate) — confirms entitlements, regions, destinations
  2. Step 14: Deploy to BTP — MTA build, CF push, smoke test

What Bedrock is called for

Every substantive generation step calls Bedrock: FD analysis, solution design, ABAP code, code review, test pack, TD generation, challenger review, package summary. ~5–8 Bedrock calls per full run. Prompt caching (1.4–1.6M cached tokens/run) keeps cost at ~$2.25.

CP = human checkpoint. Engine pauses and waits — never auto-approves. Every approval is recorded in run.json.
Slide 4 — Public Cloud Brain

Inside the Public Cloud Brain

Three layers of knowledge that make every pipeline run smarter than the last. Anti-hallucination by design.

Layer 1 — Object Graph

File: graph.json (9.2 MB) · Rebuilt in ~90 seconds

A graph of 8,900+ released SAP CDS views, APIs, BAdIs and their relationships. The MCP tool get_object_graph navigates it to find what a requirement can consume. Tells the engine: "this BAdI fires here, these CDS views expose those fields."

POC: JSON file on EC2 disk  |  Production: S3 + in-memory cache

Layer 2 — Vector Index

File: index.json (2.0 MB) · Rebuilt in ~3 seconds

Dense embeddings (sentence-transformers) or TF-IDF fallback of the entire catalog. semantic_search finds APIs and BAdIs by meaning, not just keyword. Example: "get open purchase orders for a supplier" → surfaces API_PURCHASEORDER_PROCESS_SRV.

POC: JSON file on EC2 disk  |  Production: RDS PostgreSQL + pgvector

Layer 3 — Experience Graph

File: experience_db.json · Grows with every run

Every completed pipeline run is recorded (anonymised — client names hashed). find_similar_delivery surfaces proven extensibility approaches for similar requirements. "You've solved this before — here's what worked."

POC: JSON file on EC2 disk  |  Production: RDS PostgreSQL + pgvector

Catalog DB

File: catalog.db (1.5 MB SQLite)

The authoritative seed of released SAP objects — 8,900 CDS views, 500+ APIs, 1,200+ BAdIs. Synced from SAP Business Accelerator Hub. Powers check_object_release_state (the anti-hallucination gate that rejects BAPIs and classical objects).

POC: SQLite file on EC2 disk  |  Production: RDS PostgreSQL

Slide 5 — Security

Security architecture

No API keys stored anywhere. Every credential is either auto-rotating (IAM) or passed via environment variable at startup.

Credential model

CredentialHow managedWhere stored
Bedrock accessIAM instance profile — AWS rotates automatically every few hoursNowhere (ephemeral)
S3 accessSame IAM instance profileNowhere (ephemeral)
SAP credentials (live mode)Environment variable S4PC_SAP_* at startupNever in files or logs
App access passwordEnvironment variable S4PC_ACCESS_PASSWORDNever in files or logs
Anthropic API keyNot used. Claude Code seats are the runtime.N/A
Work Zone OAuth2 client secretBTP Destination service (client's BTP account)BTP credential store

Network security

LayerRule
ALB security groupAccept 443 from 0.0.0.0/0 (or Work Zone IPs only)
EC2 security groupAccept 443 from ALB security group only — never from internet
EC2 security groupAccept 22 (SSH) from team VPN/IP range only
RDS security group (prod)Accept 5432 from EC2 security group only
S3 bucket policyAllow GetObject/PutObject from EC2 IAM role ARN only

Authentication flow (user → pipeline)

  1. User's identity is verified by the client's own XSUAA / IAS before the tile opens
  2. Work Zone destination adds OAuth2 bearer token or mTLS cert to the HTTPS request
  3. ALB forwards request to EC2 — token validated at ALB listener rule (optional) or at webapp
  4. Webapp checks S4PC_ACCESS_PASSWORD for additional layer (HTTP Basic)
  5. All actions logged to CloudWatch with timestamp — full audit trail

What never leaves AWS

  • System prompts — phase instructions, governance rules, CLAUDE.md
  • Brain content — catalog, graph, vectors, experience
  • MCP server logic — release checks, lint rules, advisor decision tree
  • Engine executable — Claude Code CLI and its session state

Only a URL and the output deliverables (FD, TD, ABAP code, test pack) cross the boundary to the client.

Audit trail

  • mcp-server/logs/audit.jsonl — every MCP tool call (tool, args, verdict, timestamp)
  • webapp/logs/usage.json — per-run token usage and cost
  • output/<RUN>/run.json — all human decisions and approval timestamps
  • CloudWatch Logs — all stdout/stderr from webapp and engine
MCP server runs in offline mode by default — live SAP API calls require explicit opt-in and are rate-limited and audited.
