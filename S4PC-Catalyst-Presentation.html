The Problem We Solve
SAP Public Cloud forces discipline. Most teams don't have tooling that enforces it.
🚫

Classical ABAP is Forbidden

No BAPIs, no function modules, no user exits, no dynpros, no SAPscript. Every non-released object is upgrade-unsafe and will not compile on Public Edition.

📋

Released Objects Must Be Verified

Every API, BAdI, CDS view, and class needs a C1 release contract. Relying on memory leads to hallucination — wrong objects that fail ATC checks on the tenant.

⚠️

Inconsistent Delivery Quality

Without automated gates, code quality varies by developer. Review cycles are expensive and catch issues late — after build, not before.

🔍

Three Extensibility Modes — Easy to Get Wrong

Key User, Developer (ABAP Cloud), and Side-by-Side (BTP) each have different constraints, cost profiles, and upgrade behaviour. Wrong choice = rework.

💸

BTP Services Have Real Cost

Every side-by-side service runs on consumption billing. Proposals without cost lines are incomplete — and no tooling enforces that cost is documented.

🧠

LLM Hallucination Risk is High

SAP-specific knowledge (released objects, BAdI names, API endpoints) is sparse in public training data. LLMs confidently produce plausible but wrong SAP artifacts.

How Agents Interact
Sequential pipeline with gate enforcement — no agent can bypass a checkpoint

🔄 Orchestration Model

The Delivery Lead spawns each specialist as an isolated Claude Code subprocess. Each agent reads run.json (the shared state file) + its assigned deliverables, does its work, and writes results back. The Delivery Lead then evaluates the gate verdict before handing off to the next step.

✋ Human Gate Mechanics

At CP1, CP2, and CP3 the Delivery Lead sets run.json.status = "awaiting_approval" and checkpoint_request. The pipeline stops. The webapp surfaces the decision panel. No agent resumes until the human submits Approve / Adjust / Reject via the UI.

🚫 Gate Failure Behaviour

A FAIL verdict at any gate terminates the current phase. The human must review findings, apply fixes, and resume. Automatic retry is not allowed — every gate failure is a human decision point. This prevents runaway cost from repeated agent loops.

The s4pc MCP Governance Server
Why it was built — and why a general LLM cannot replace it

❌ Why Not Just Ask the LLM?

SAP Public Cloud has strict, evolving rules. General LLMs produce plausible but wrong SAP object names, BAdI names, and API paths. There is no way to fine-tune Claude with the exact, up-to-date SAP released-object catalog. Hallucinated objects cause ATC failures, upgrade breaks, and project rework.

✅ Offline-First, Zero LLM Calls

The MCP server is a pure Python 3.9+ stdlib process — no external dependencies, no network calls in offline mode. It reads a local SQLite catalog (catalog.db) at startup and answers governance questions instantly. No LLM is involved in any governance decision.

📋 Audit Trail

Every tool call is logged to mcp-server/logs/audit.jsonl with timestamp, tool name, arguments, and verdict. Every pipeline run is traceable: which objects were checked, what verdict was returned, which authoritative source was cited.

Cost Optimisation Strategies
Seven deliberate choices that reduce token and infrastructure cost
🎯

1. Model Tiering — Opus Only Where It Matters

Opus (3× more expensive than Sonnet) is used only at the 3 decision/review gates where reasoning depth directly affects quality. Sonnet handles all execution steps (orchestration, build, tests). Result: ~70% of tokens are billed at Sonnet rates.

📴

2. Offline MCP — Zero LLM Calls for SAP Facts

All SAP catalog lookups (released objects, lint, BAdI search) run against local SQLite (catalog.db) — zero tokens consumed. The MCP server answers in milliseconds with no API cost. Live mode (real tenant queries) is optional and rate-limited.

🚦

3. Early Exit on Gate Failure

If the Release Check gate (Step 4) fails, the pipeline stops before Developer, Reviewer, Test Agent, and Challenger all run. A failure caught at Step 4 costs ~2 agent calls instead of 6. Gates are ordered cheapest-to-most-expensive on purpose.

📝

4. Structured Prompts, Not Open Conversations

Every agent receives a highly structured prompt (phase prompt) that limits scope to exactly the current step. There is no open-ended dialogue or back-and-forth — each agent call is a single bounded task. This minimises context inflation.

♻️

5. Fresh Context Per Phase

Each phase (A, B, C, D) spawns fresh agent sessions. There is no single long-running conversation accumulating context. Each agent reads only the deliverables it needs — not the entire session history. Context cost stays bounded.

🔁

6. Human Gates Prevent Expensive Rework Loops

The 3 human checkpoints exist precisely to catch direction errors before they propagate. Approving at CP1 confirms the approach before any code is written. Catching a wrong extensibility choice at CP1 costs 3 agent calls; catching it at CP3 costs all 6.

💾

7. Build-First TD — No Spec Drift Cost

The Technical Design is written after the code — not before. This eliminates the classic cost sink of iterating the TD to match the code, or re-building code to match a revised TD. One pass, one write.

Technology & Methodology
What's under the hood — and why each choice was made
AI & Agent Layer

Claude Code (Anthropic)

The LLM runtime. Claude Code is the CLI — agents are spawned as headless subprocesses with -p <prompt> --output-format stream-json. No API keys in code — the subscription covers all agent calls.

Multi-Agent via Agent SDK

Each specialist is a separate Claude Code process. The Delivery Lead orchestrates via shared filesystem state (run.json). No inter-agent RPC — clean, auditable, restartable.

MCP (Model Context Protocol)

The s4pc server exposes 16 governance tools to Claude Code via the MCP stdio transport. Registered in .mcp.json. Python 3.9+ stdlib — zero pip installs required.

Generated Artifacts

ABAP Cloud / RAP

RAP business objects (CDS + behaviour), Fiori Elements UIs, released BAdI implementations, Application Jobs — all in "ABAP for Cloud Development" language version. OO-only, English, no hard-coding.

CAP Node.js + UI5

For BTP side-by-side: CAP Node.js service + SAP UI5 frontend + XSUAA auth + Destination Service. Packaged as MTA (mta.yaml), built with mbt, deployed with cf deploy.

Adobe LiveCycle (Forms)

Adobe Forms only — no SAPscript or Smart Forms (both forbidden on Public Cloud). Form templates deployed via the Maintain Form Templates app.

Platform & Methodology

SAP S/4HANA Cloud Public Edition

3-system landscape (Dev/QA/Prod). All rules are enforced at the tooling level — not advisory. Git-based ABAP Cloud software components. ADT (Eclipse) for ABAP development.

Build-First Methodology

Inspired by TDD's "make it work, then document": approve the approach (CP1), lock object names, build the code, then write the TD. Prevents the TD/code drift that costs rework time on traditional projects.

Human-in-the-Loop (HITL)

Mandated by design. The pipeline never auto-approves or continues on silence. Mimics professional code review: the AI proposes, the human decides. Three hard stops that cannot be bypassed.

Security Architecture
Credentials never leave the machine — by design, not by policy
🔑

No API Keys in Code or Files

Claude Code is the LLM runtime — no ANTHROPIC_API_KEY in any file, environment variable, or subprocess. The key is never passed to headless agent subprocesses (_env.pop("ANTHROPIC_API_KEY") is enforced in the engine).

💾

SAP Credentials: Environment Variables Only

Communication user credentials for S/4HANA Cloud live in environment variables — never in files, never in logs, never in git. The MCP server reads them at startup and never re-serialises them.

🧹

BTP Tokens: Session-Only, In-Memory

Bearer tokens and passwords entered in the BTP Connections panel are stored in _BTP_SECRETS — a Python dict that exists only while the webapp is running. Webapp restart clears all credentials. Nothing is written to disk, git, or logs.

🏠

Isolated CF_HOME Per Deploy

Each BTP deploy uses a fresh tempfile.mkdtemp() as its CF_HOME. The temp dir is deleted in the finally block after every deploy — success or failure. No credential cross-contamination between different client systems.

📋

Audit Log for All Governance Decisions

Every MCP tool call (release check, lint verdict, advisor recommendation) is written to mcp-server/logs/audit.jsonl with timestamp, arguments, and result. Full traceability for compliance reviews.

🔒

Read-Only Live Mode

When the MCP server connects to a real S/4HANA tenant (live mode), all OData calls are strictly GET-only. No write, create, or delete operations are permitted. Allowlisted endpoints, rate-limited, audited.

Why No Super Agent?
Structured orchestration vs dynamic routing — a deliberate cost and quality decision
❌ Super Agent Approach (what we avoided)

What a super agent does

A super agent (meta-agent / orchestrator) sits above all specialist agents. At every step transition it reads all previous outputs, reasons about current state, and dynamically decides which agent to call next, whether to retry, or whether to re-plan entirely.

Used in: AutoGen GroupChatManager, LangGraph supervisor node, CrewAI manager agent.

Cost in a 12-step pipeline

What it does at each stepToken cost
Reads all previous agent outputs to route~8k–80k input tokens per step
12 step transitions × 1 Opus reasoning call12 extra Opus calls
Context grows with every step (accumulates)80k+ tokens by step 10
Re-planning if gate failsAdditional Opus loops
3–4× more expensive per pipeline run
And adds no quality — it's routing a fixed sequence that is already known

The core problem with a super agent here

A super agent is designed for open-ended, unpredictable tasks where the next step cannot be known in advance. In S4PC Catalyst, every RICEFW delivery follows the same 12-step sequence. Paying an Opus model to "decide" Step 4 comes after Step 3 — which is already encoded in the Skill — is pure waste.

✅ S4PC Structured Orchestration (what we built)
Skills (SKILL.md)

Encode the fixed pipeline sequence in a text file. Replaces the super agent's "which step next?" decision. Cost: zero tokens — read at session start, not re-evaluated at every step.

run.json

Shared state file on disk. Every agent reads exactly what it needs without a super agent passing context between them. Replaces "synthesise all previous outputs" at each step. Cost: zero tokens — a file read.

MCP Gates

Release check, lint, peer review all return a binary verdict (PASS / FAIL / SHIP / FIX). No super agent reasoning needed — the gate is a pure function. Replaces "reason about whether to proceed." Cost: zero tokens — local computation.

Human Gates ✋

CP1 / CP2 / CP3 handle the one place where dynamic judgment genuinely matters — a human decides better than any AI super agent at a SAP delivery checkpoint. Replaces "should I continue or re-plan?" at each approval point. Cost: zero tokens.

Delivery Lead

A lightweight Sonnet orchestrator — not Opus. It reads run.json, sees the current step, spawns the next defined agent. No reasoning about routing. Cost: Sonnet rate (~3× cheaper than Opus), called once per phase.

Net result: same quality, fraction of the cost

Authentication Flow (happens on first request)
1
User opens approuter URL
Approuter checks session cookie — none found → initiates OAuth2 flow
2
Redirect to XSUAA → redirect to IdP
XSUAA sends user to Azure AD (or custom SAML IdP) for login. Requires: Trust Configuration in BTP Cockpit (manual).
3
IdP issues SAML assertion → XSUAA exchanges for JWT
JWT contains user email, IdP groups, and granted scopes from role collections
4
Approuter checks Role Collections
Checks JWT for required scope. Requires: Role Collection assigned to user in BTP Cockpit (manual). No role = 403.
5
Request proxied to CAP with JWT
Approuter forwards request to po-viewer-srv. CAP validates JWT via @sap/xssec + passport. Session established.
Data Flow (every OData request)
6
CAP handler enforces server-side rules
Adds PurchaseOrderStatus = 'B' filter + 500-row cap. Client cannot override these — security by design.
7
Destination service resolves S4HC_PO_API
CAP calls Destination REST API → gets S/4HC URL + credentials. Requires: destination named S4HC_PO_API manually created in BTP Cockpit.
8
OData v2 call to S/4HANA Cloud
CAP issues GET to API_PURCHASEORDER_PROCESS_SRV with comm-user credentials. Response: JSON with PO list.
9
CAP transforms v2 → v4, returns to browser
CAP auto-converts OData v2 response to v4 JSON format. Approuter adds security headers. Browser renders data.
