Step 0 · the request

The prompt arrives in business language.

This is the normal case, not a simplified one. A requirement arrives describing an outcome, and contains no SAP object names at all.

// the requirement, exactly as written

"Build a search so a consultant can find project work packages
 and add themselves to the delivery team."

What is not in that sentence

No API. No CDS view. No BAdI. No scope item. Nothing the object catalog can be queried with directly — because the person writing a requirement has no reason to know SAP's internal naming.

So the first job is translation

Turning an outcome into candidate object names is work, and getting it wrong is how a design ends up citing something that does not exist. That is Layer 2's entire purpose — and why it runs first.

The request02 / 09
Read the requirement out loud. The point lands better spoken than on the slide: there is nothing in it a catalog could look up. Every step that follows exists because of that gap.
Step 1 · Layer 2 · semantic index

Turn the words into candidates.

The agent cannot ask Layer 1 yet — it has nothing to ask for. Layer 2 is the only layer that bridges business language to SAP naming.

semantic_search("project work package resource assignment")
Candidate returnedTypeWhy it matched
I_EngagementProjectItemCDS viewthe work package itself
I_EngagementProjectResourceCDS viewwho is assigned to it
_CPD_SC_PROJ_ENGMT_CREATE_UPD_SRVAPIthe service that writes an assignment

Nobody would guess I_EngagementProjectItem from "work package". The phrase and the object name share almost no words. Layer 2 matches on meaning, which is exactly the gap an exact-match catalog cannot cross.

Step 1 · L203 / 09
If asked how the matching works, "it compares meaning, not spelling" is enough. Resist going into embeddings — the interesting part is the next slide, where these candidates get checked.
Step 2 · Layer 1 · object graph

Layer 2 returns plausible. Layer 1 decides real.

Every candidate is checked against the released-object catalog before it is allowed into a design. This is where governance actually happens.

check_object_release_state("I_EngagementProjectItem")
  → LIKELY_RELEASED · evidence: catalog_hit

get_object_graph("I_EngagementProjectItem")
  → 22 connected objects, each with its own verdict

A name that survives

Comes back catalog_hit — a real entry in the released catalog. Citable, with a note to confirm on the SAP Business Accelerator Hub.

A name that does not

Comes back naming_heuristic_only — the name looks like SAP's convention and nothing in the catalog backs it. Usable as a placeholder, never written up as released.

The graph then widens the picture. Twenty-two connected objects is the released landscape a designer can legally reach from here — the APIs, views and BAdIs around the thing they started from.

Step 2 · L104 / 09
The two boxes are the heart of the whole system. Same verdict shape, opposite standing. If someone only takes one thing from this deck, make it "read the evidence, not the verdict".
Step 3 · Layer 3 · experience

Have we done this before?

Two questions, both answered from our own delivery history: is there a comparable build, and what did we learn the hard way?

find_similar_delivery("project work package search and team assignment")
  → SMART-SEARCH-FD · score 0.72 · completed · 3/3 gates passed

query_experience("work agreement resource assignment")
LessonWhat it says
EXP-024resolve the personnel number in the query provider, and fail soft
EXP-027no SELECT SINGLE on overlapping work agreements
EXP-034a RAP custom entity forces satellite objects — name them at the first checkpoint
EXP-035release the custom CDS view with C2 before publishing the Custom Logic

EXP-027 is the one that earns its keep. Work agreements overlap in time, so a single-row read silently returns the wrong one. Somebody discovered that by shipping it. Every design after theirs starts already knowing.

Step 3 · L305 / 09
Land EXP-027 specifically — a concrete, unglamorous bug is far more convincing than the abstract claim that the system "learns". This layer grows with every completed delivery, automatically.
Step 4 · Layer 4 · learning corpus

What have we written about it?

Functional designs, technical designs, test and cutover material, and SAP's own process documentation — searched by meaning and filtered to the phase that matters.

search_brain("project work package staffing", phase="Explore")
  → prior FDs and TDs, each hit carrying `objects_mentioned`

Why the phase filter matters

A cutover checklist and a functional design answer different questions. The corpus is faceted by SAP Activate phase, deliverable type and role, so an Explore-phase question is not answered with a Deploy-phase document.

Every document is dated

The corpus holds multiple revisions of the same artifact. A superseded revision is flagged as such, so an old version is never quoted as though it were current.

But a document is not a claim that its objects are still released. It records what was true when it was written. That single sentence is why there is a fifth step.

Step 4 · L406 / 09
End on the callout and pause. It sets up the next slide, which is the one worth slowing down for.
Step 5 · Layer 1 again · the mechanic that matters

Old thinking. Today's facts.

Every SAP object name that Layer 4's documents mention is re-checked against the catalog as it is now — not as it was when the document was written.

_CPD_SC_PROJ_ENGMT_CREATE_UPD_SRVSTILL VALID
VerdictLIKELY_RELEASED
Evidencecatalog_hit
Named ina past design document

Cite it. The document's approach and the object both hold up today.

CE_PROJECTBILLINGREQUESTWITHDRAWN
VerdictNOT_AVAILABLE
Evidencecatalog_retired
Named inthe same past design document

Refuse it. Genuinely released when that document was written. SAP has since withdrawn it.

This is what a human review would miss. The document is correct, well written and was right at the time. Nothing in it looks wrong. Only the current catalog knows the object is gone — and twenty-five objects were in exactly that state when the check was added.

Step 5 · L1 again07 / 09
Slow down. The argument is: you get the experience without inheriting its mistakes. If asked how you would catch this manually — you would not. That is the honest answer and it is the strongest one.
The shape of it

The order is not fixed.

People expect four layers queried once each, in order. That is not what happens — and the difference is the design.

L2 discover L1 verify L3 precedent L4 documents L1 verify again
LayerWhat it contributed to this one question
L2 · meaningthree candidate objects, from a sentence containing none
L1 · grapha verdict and evidence tier per object, plus 22 connected objects around them
L3 · experienceone comparable delivery and four lessons that change the design
L4 · corpusthe documents — with every object they name re-verified

Layer 1 runs twice, for different reasons. Once to check what Layer 2 guessed. Once to check what history asserted. A design that only did the first would still cite a withdrawn object.

The comparison

The same prompt, without the brain.

A general model

Returns SAP object names. Fluent, well-formed, and confident.

No verdict. No evidence. No indication which names it is sure about.

No knowledge that this team already built something similar, or what went wrong.

No idea that one of those objects was withdrawn by SAP.

The same prompt, grounded

Every object carries a verdict and the evidence behind it.

Four lessons from previous deliveries, cited by id.

One comparable past build, with its approach and its gates.

A withdrawn object refused, not quietly reused.

The names look identical in both columns. That is the difficulty — a fabricated SAP object name is exactly as plausible as a real one, and so is one that was retired last quarter. Making that difference mechanical, rather than a matter of someone's recall, is the entire product.

The comparison09 / 09
Close on the callout, not on a summary. The line to land is that plausibility is not a signal — it is the problem. Then stop talking.
