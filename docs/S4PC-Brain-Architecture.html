Why build this at all

A general model will invent an SAP object name — confidently.

On Public Edition, clean core is a platform constraint, not a preference. Only C1-released objects compile and survive upgrades. A wrong object name is not a typo — it is a redesign, discovered at build time.

The failure mode

Ask any LLM for "the API for material stock" and it will produce a plausible, well-formed, entirely fictional name. Nothing in the answer signals which is which.

Why review misses it

A fabricated name and a real one look identical in a design document. The reviewer would have to check every object by hand against three separate SAP lists.

What the brain changes

Every object gets a verdict and an evidence field. Fabrication is detectable mechanically, and the pipeline gates on it.

This is not a search problem. Search returns what looks relevant. Governance returns what is defensible — with the source named, so a human can check it in the tenant.

Two layers are derived, so the brain monitors itself. L1 and L2 are rebuilt from the catalogs and the corpus, which means they can fall behind their sources — and a layer that has fallen behind returns less, which looks identical to a correct answer. layer_health compares every derived store against its source on demand and names the exact rebuild needed. Rebuilds are also automatic: on startup, after a catalog sync, and after every completed delivery.

Layers · Detail04 / 17
If someone asks why "derived" is called out: L1 and L2 are rebuilt from the catalogs and corpus, so they can silently drift. That is the one failure that does not announce itself — the search just returns fewer rows, which is indistinguishable from a correct empty result. layer_health exists so an agent can tell "we have no lesson about this" apart from "the index needs rebuilding." If pressed on whether a layer is behind right now: layer_health answers that on demand, and a rebuild is one command plus an automatic one on the next completed delivery. That is the check doing its job rather than a problem to explain — say so plainly and move on.
Connection model

One question. Five stages. One answer with its evidence.

The layers are not four separate search boxes. A question fans out to retrieval, narrows to a candidate object, fans out again to corroboration, and converges on a governed verdict.

Connection model05 / 17
The shape is the message: fan out, narrow, fan out, converge. Say it in that order. The dashed rust line at the bottom is the closed loop — L3 is the only layer we write back to, and it is written at package time, so every delivery makes the next one better. That loop is what makes it a brain rather than an index. Precise if asked: one trace is four fixed calls plus one governance call per candidate object, capped at three — so three to seven tool calls, typically well under ten seconds. If retrieval surfaces no object at all, the graph and governance stages are skipped rather than faked, and the panel says so.

Consumer A

The 12-step pipeline is one consumer — not the brain itself.

Our delivery pipeline wires the brain into three automated gates and three human checkpoints. Useful, but it is an application on top of the brain. Nothing about the brain assumes it.

1 Intake 2 Solution proposal 3 Object verdicts 4 GATE 1 · Release check 5 ✋ CP1 · Solution approval 6 Build 7 GATE 2 · Code review 8 Lint 9 Unit test design 10 Technical design 11 GATE 3 · Peer + challenger 12 Package

Where the brain binds in

Step 3 takes a verdict for every object. Gate 1 fails only on NOT_AVAILABLE. Step 8 lints every ABAP snippet. Step 12 writes a lesson back to L3.

Humans are mandatory

Three checkpoints stop and wait for an explicit decision. Never assumed, never continued on silence — every decision is recorded in the run.

What it produces

Deliverables plus a lint verdict, a release-state table and a tenant verification checklist — the evidence trail a reviewer can actually audit.

What that changes

Without the brain, a design question naming an SAP app or service is the model's best recollection — confident, unsourced, and occasionally an object SAP withdrew two releases ago.

With it, the same question arrives carrying SAP's process text, our own precedent, and a release verdict per object. Same agent, same effort — defensible instead of plausible.

Deployment · AWS us-east-1

Two front doors, one host.

Where the knowledge actually lives

All four layers are files on the instance's EBS volume — the released-object catalog, the object graph, the semantic index, the document corpus, and every delivery's outputs. No managed database, nothing to provision.

That is a POC choice with a known trade: it is simple, cheap and fast, and it ties durability to one volume's backups. The scale path is designed and not switched on.

It refreshes itself

A scheduled job re-pulls SAP's released-object catalog, rebuilds the semantic index and the object graph, and re-derives business areas. The index also rebuilds after every completed delivery, so a new lesson is searchable without anyone asking.

This is why a withdrawn SAP object stops being reported as released — the refresh is what keeps the verdicts honest.

No LLM API keys anywhere. Embeddings and inference both run on Amazon Bedrock through the EC2 IAM instance profile — so there is no Anthropic account, and no key, on the critical path.

Deployment · AWS12 / 17
The one-host point is deliberate: this is a POC footprint, and the scale path (RDS pgvector, an autoscaling group, per-client isolation) is designed but not switched on. If asked about cost, the honest answer is that it is one t3-class instance plus Bedrock usage per query. Do not oversell the infrastructure — the value is the governance model, not the topology.

Integration · client landscape

Three sources in. Nothing written back.

The brain is read-only by design. It grounds our agents in SAP's own facts and our own delivery history — it never changes a client system.

1 · SAP's product catalog

Public, no client involvement. Released APIs, CDS views, BAdIs, business events and the 679 scope items, pulled from the SAP Business Accelerator Hub. Refreshed monthly, so a newly deprecated object stops being reported as released.

This is what makes a release verdict defensible rather than a guess.

2 · The client tenant optional

Read-only, allowlisted, opt-in. For grounding a design in the tenant's actual field names rather than assumed ones. Requires a communication user; every call is rate-limited and written to an audit log.

Off by default. The brain is fully useful without it — this only adds precision.

3 · Our delivery documents

Our own work products — functional and technical designs, test, cutover and change material, harvested from our SharePoint. Names and identifiers are masked on ingest, before anything is indexed.

This is the layer that makes the brain OURS rather than a generic SAP reference.

What a client gets, and what it costs them. Nothing to install, no change to their landscape, and no write access requested. The one prerequisite before the brain serves a second client is per-client isolation of the delivery layer — the product catalog is shared by nature, but delivery history is not, and that separation is built before the second engagement, not after.

Integration · client landscape14 / 17

The isolation point is deliberate: name it before they ask, because the second engagement is when it matters.
Integration · the delivery platform

The dashboard runs the work. The brain answers the questions.

Two separate things on one host, deliberately. The dashboard owns what happens; the brain owns what is true. Neither reproduces the other.

The dashboard — the delivery surface

Launches a delivery from a Functional Design, shows every step live, and stops at the human checkpoints for an explicit decision.

Runs the model server-side on AWS Bedrock under an IAM role — no personal AI account, no key, nothing for a teammate to install.

Reached over the internal network on the VPN. A browser is the only requirement.

The brain — the governance layer

Every step of every delivery calls it for release verdicts, prior designs, lessons and object relationships.

Published separately as an authenticated endpoint, so an agent outside the dashboard gets identical answers.

Why the separation matters commercially

The brain is the asset. The dashboard is one way to use it. An agent built next quarter, by a different team, in a different tool, inherits the same governed facts on day one.

Onboarding an agent does not change the brain. That is the whole point of the design — and it is why 40 agents is a catalogue exercise, not 40 integration projects.

Knowledge compounds. Every completed delivery adds lessons and a searchable record, automatically, and every agent sees them.

One number worth remembering. The brain does not hold a copy of anything the dashboard shows. The dashboard reads the brain live, so there is exactly one version of the truth — and no reconciliation step to get wrong.

Integration · the delivery platform15 / 17

Plan of action · scaling to the agent catalogue

Adding an agent is a registry entry, not a project.

Each agent gets a card in the dashboard and its own run view. What it does not get is its own knowledge base — that is the discipline that makes the catalogue scale.

Step 1 — declare it

One entry in the agent catalogue: name, phase, what it does, what inputs it needs, which checkpoints it stops at. The card, the start form and the run view are generated from that entry.

Step 2 — declare what it may see

Which relationships, which confidence floor, which tools. A functional agent sees process and scope relations; a build agent sees object and code relations. One brain, different views — not different data.

Step 3 — only if it needs new knowledge

Extend the model with a new entity and its relationships. Never a new store. If an agent seems to need its own database, the model is missing a concept — so we add the concept.

Worked example — a functional agent

A key-design-decision agent needs process knowledge the brain did not hold, so the obvious move is a process database of its own.

We added three relationships instead: scope item → process → process step → released object. Live today.

The functional agent now answers "which step needs which object, and is that object still released" — and every other agent gained the same chain for free.

Process content comes from Signavio. Where SAP states the link it is recorded as declared; where a client has modelled their own variant it is recorded as observed. An agent can ask for one and not the other.

The sequence we are following. Prove the run view and the checkpoint controls against one agent first, then the grid of 40. A card list will always work; the run view is where the design either holds or does not.

Plan of action · agent onboarding16 / 17
The message is that scaling is bounded work, not 40 unknowns. The three steps are the actual mechanism, not a simplification. Next — in this order

1. The agent catalogue. 40 agents on the dashboard, each a registry entry over the same brain. Run view and checkpoint controls proven against one agent first, then the grid.

2. The process layer at scale. Signavio process content across the scope items in play, so functional agents work from SAP's own process model rather than from prose.

3. Live tenant grounding. Read-only, per engagement — designs validated against the tenant's actual fields, and the per-object detail SAP's public catalog does not publish.

4. Knowledge compounding. Every completed delivery already adds lessons and a searchable record automatically. This improves with use rather than with investment.

Prerequisites before wider rollout

Transport security and per-user identity. The dashboard runs inside the corporate network behind a shared credential today. TLS and named sign-in are required before the audience widens beyond the delivery team — partly for protection, partly so an approval is attributable to a person.

Per-client isolation. The SAP product catalog is shared by nature; delivery history is not. Separation is built before a second engagement, not after.

One policy approval. The endpoint URL needs to be on the approved-tools list so teammates can attach the brain in their own editor. Request in flight; nothing else waits on it.

Where it is deliberately incomplete

Business-area coverage. 271 objects carry a curated area; propagation adds 1,129 more at a measured 98.3% precision. That is 11.9% of the graph, and derived values are labelled as derived rather than merged in — so a browse by area is visibly partial rather than quietly wrong.

Object-level detail. SAP's public catalog publishes names and release states, not the internals of each object. Those come from a connected tenant, which is item 3 opposite. Until then the brain says it does not know, rather than guessing.

The ask. Two things. Approve the endpoint for the approved-tools list, so the wider team can use the brain from their own editor. And name the next delivery to run through it — the knowledge layer grows on real engagements, not in a lab, and the next one is worth more to us than the last.
